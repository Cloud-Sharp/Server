# HTTP 요청 멱등성 공통 구조 기획

새 변경 API가 `Idempotency-Key` 지원을 선언하면 공통 필터와 PostgreSQL 저장소를 사용해 중복 실행을 막고 최초 결과를 복구할 수 있게 한다. 공통 구조의 완료 기준은 새 API를 추가할 때 공통 필터, 실행 흐름, 테이블 스키마를 바꾸지 않고 연결할 수 있는 것이다. 검증에는 이 구조에 연결된 테스트용 엔드포인트를 사용한다. 기존 API의 전환은 각 API의 적용 작업에서 결정한다. [API 멱등성 결정](decisions/api-idempotency-and-admin-audit.md#http-요청-멱등성)

## 새 API 연결 방식

라우트에 멱등성 적용을 선언하고 다음 계약을 제공한다.

| 연결 항목 | 새 API가 제공하는 정보 |
|---|---|
| 작업 식별자 | 저장한 결과를 올바른 응답 변환기로 연결하는 안정적인 작업 이름과 결과 형식 버전 |
| 요청 범위와 지문 | 기본값은 요청자·HTTP 메서드·표준 경로 범위와 정규화한 본문·미디어 유형·의미 있는 쿼리의 지문이다. 익명 작업의 요청자 식별 방식이나 처리 결과에 영향을 주는 조건 헤더 등은 작업별로 지정한다. |
| 완료 결과 | 업무 트랜잭션 콜백의 결과 타입, 복구용 데이터 변환, 그 데이터로 HTTP 응답을 구성하는 변환을 등록한다. 일회성 비밀 발급 작업은 완료 사실과 공개 가능한 식별자를 보관한다. |

표준 경로에는 실제 대상 리소스를 식별하는 경로 값이 포함된다. 경로에 비밀 토큰이 있으면 해시를 사용한다. 적용을 선언한 라우트는 출력 가능한 ASCII 문자로 구성된 16~128자 키 하나를 요구한다. 키가 누락되거나 형식이 잘못되면 `400 REQUEST_VALIDATION_FAILED`를 반환한다. 최초 요청과 재시도는 모두 해당 라우트의 인증·인가를 거친다. 완료 여부는 만료, 잔여 수량처럼 최초 업무 실행에만 적용하는 상태 검증보다 먼저 확인한다.

## 요청 처리와 레이어 경계

공통 엔드포인트의 등록과 실행 순서는 필터 설계에서 정한다. 요청 시작과 선점 해제는 Core 유즈케이스 설계에서 정한다. [HTTP 요청 멱등성 필터 설계](api/http-idempotency-filter-design.md) · [Core 요청 멱등성 유즈케이스](use-cases/idempotency-use-cases.md)

- **API 필터**는 헤더를 검증하고 요청 범위·지문을 구성한다. 새 실행 시도에는 요청 범위의 `IIdempotencyTransactionContext`에 선점과 결과 변환 정책을 등록하고 핸들러를 호출한다. 저장된 결과는 최초 상태 코드·본문과 필요한 `Location` 및 `ETag`로 복원한다. 일회성 비밀 발급의 완료 결과는 `409 SECRET_RESPONSE_NOT_REPLAYABLE`로 변환한다.
- **Core**는 요청 시작과 선점 해제 유즈케이스 및 저장소 포트를 제공한다. 업무 유즈케이스는 기존 `IUseCase.ExecuteAsync`와 `ITransactionExecutor.ExecuteAsync`로 실행한다. [Core 트랜잭션 계약](../src/CloudSharp.Core/Abstractions/Transactions/README.md#실패와-취소)
- **Infrastructure**는 선점·잠금·완료 기록·결과 조회를 PostgreSQL로 구현한다. `EfCoreTransactionExecutor`는 해당 요청의 컨텍스트와 일치하는 타입의 업무 트랜잭션을 처리하며, 기존 업무 콜백을 그대로 호출하고 커밋 전에 복구 결과를 기록한다. 현재 정책은 작업당 결과 타입이 지정된 업무 트랜잭션 하나를 대상으로 한다. 같은 업무 트랜잭션의 실패 재시도에는 선점이 유지된다. [EF Core 트랜잭션 실행기](../src/CloudSharp.Infrastructure/Persistence/Transactions/EfCoreTransactionExecutor.cs)

외부 시스템에서 나중에 수행할 작업은 PostgreSQL에 접수 결과와 Outbox 이벤트를 함께 커밋하고, API 재시도에는 최초 접수 결과를 돌려준다. 외부 처리의 중복 방지는 소비자가 담당한다. [Transactional Outbox 설계](adr/use-case-logging-decorator.md#업무-이벤트와-transactional-outbox)

## PostgreSQL 저장과 복구

전용 테이블 `idempotency_requests`에 다음 정보를 보관한다.

| 데이터 | 용도 |
|---|---|
| 요청 범위와 키 | `UNIQUE` 제약으로 동일 범위와 키의 선점을 하나로 제한한다. |
| 요청 지문 | 저장된 요청과 재시도의 입력을 비교한다. |
| 상태·실행 시도 ID·선점 만료 시각 | `IN_PROGRESS`와 `COMPLETED`를 구분하고, 현재 실행 시도의 소유권을 확인한다. |
| 작업 식별자·결과 형식 버전·복구 결과 | 승인된 업무 결과 또는 재생 제한 정보를 `jsonb`에 보관한다. 토큰, 비밀번호, 인증 헤더, 토큰이 포함된 URL은 복구 결과에서 제외한다. |
| 완료 시각·결과 만료 시각 | 완료 결과를 24시간 보존한다. 만료된 완료 기록은 경쟁 요청과 원자적으로 교체하며, 사용하지 않은 만료 기록은 정리한다. |

1. **선점 트랜잭션.** `IN_PROGRESS` 행을 삽입하고 즉시 커밋한다. 다른 지문이 이미 같은 키를 사용 중이면 `409 IDEMPOTENCY_KEY_REUSED`, 같은 지문이 처리 중이면 `409 IDEMPOTENCY_REQUEST_IN_PROGRESS`다. 완료 기록이 있으면 영속 결과를 반환한다. 선점을 먼저 커밋하므로 재요청은 업무 트랜잭션의 종료를 기다리지 않고 저장된 상태를 조회할 수 있다.
2. **업무 트랜잭션.** 선점 행을 잠그고 실행 시도 ID를 확인한 뒤 업무 콜백을 실행한다. 업무 변경과 `COMPLETED` 기록을 함께 커밋한다. 저장소 오류로 완료 기록을 남길 수 없으면 업무 변경도 롤백한다. DB 실행 전략이 트랜잭션을 재시도하는 경우에도 업무 콜백 전에 완료 기록과 실행 권한을 다시 확인한다.
3. **장애와 선점 만료.** 핸들러가 종료됐을 때 업무 트랜잭션이 시작되지 않았거나 롤백이 확인되면 API 필터가 해당 시도의 선점을 해제한다. 커밋 여부가 불명확하면 SQL에서 완료 여부를 확인한다. 선점 시간이 지나도 기존 업무 트랜잭션이 행을 잠그고 있으면 처리 중으로 돌려준다. 잠금을 즉시 확보할 수 있을 때 최신 상태를 다시 확인하고 만료된 선점의 실행 시도 ID를 교체한다. [PostgreSQL 행 잠금](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS) · [PostgreSQL `NOWAIT`](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)

선점이나 결과 조회에 필요한 PostgreSQL이 응답하지 않으면 `503 DEPENDENCY_UNAVAILABLE`을 반환한다. 업무 커밋 후 응답이 유실되면 재시도는 SQL의 완료 기록으로 복구한다.

## Redis 도입 조건

첫 버전은 PostgreSQL로 선점과 조회를 모두 처리한다. 완료 결과 반복 조회가 부하 원인으로 확인되면 Redis를 조회 캐시로 추가한다. Redis에는 SQL 커밋이 확인된 결과와 지문을 저장하고 만료 시각은 SQL의 만료 시각을 따른다. 캐시 결과도 요청 범위, 지문, 만료 시각을 확인한 뒤 반환한다. 캐시에 결과가 없거나 캐시가 장애 상태면 PostgreSQL을 조회한다. 새 실행 권한과 영속 완료 여부는 PostgreSQL에서 확정한다.

## 구현 완료 기준

- 멱등성 라우트는 정책을 등록하고 기존 업무 유즈케이스를 호출한다. 일반 라우트는 기존 트랜잭션 흐름으로 처리한다.
- 같은 키의 동시 요청에서 업무 변경이 한 번만 커밋된다. 다른 지문, 처리 중 요청, 다른 요청 범위가 각 계약대로 처리된다.
- 업무 트랜잭션 실패, 선점 만료 중 경합, 오래된 실행 시도의 복귀, 커밋 직후 응답 유실을 각각 재현한다. 커밋된 업무의 최초 결과는 PostgreSQL에서 복구된다.
- 보호된 API는 재시도 시에도 인가를 적용하고, 일회성 비밀은 영속 결과와 재생 응답에서 제외한다.
